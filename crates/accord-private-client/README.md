# Offline Esmeralda test client

This is the demonstration client used by OotleAccord's 10/10 and 7/10 escrows. It generates real native stealth proofs and encrypted outputs with Tari's wallet-crypto library. It has no network client and never submits transactions. It does not read Sapient seeds or the deployment wallet's private keys. General Sapient funding remains unavailable.

Build on Linux with `cargo build -p accord-private-client --locked`. Use `accord-private-client COMMAND .local/private-escrow .local/private-escrow/config.json` from the repository root. All recovery journals stay under ignored `.local/`; the command refuses to overwrite an existing artifact. These files contain spending keys and masks in plaintext and must be kept private and backed up. Unix files are created with mode 0600; apply equivalent private file permissions on other systems. This CLI does not provide encrypted backup management.

Public configuration fields are `payout_address` (base Esmeralda address), `creator_component`, `creator` (base public key), `reviewers` (five public keys), `deadline`, `max_epoch` and `agreement_id`. Add `component` and `authority_resource` only after verifying the constructor receipt against the agreement. `condition` saves the official condition root; add it to configuration as `condition_root` before funding. The constructor fixes a 60% threshold, required reviewer index 2 and the one-time payout key generated by `prepare`.

Optional unsigned integer fields `funding_units` and `target_units` independently set the initial contribution and goal, defaulting to 10000000 raw units each. Funding must be positive and no larger than the goal. The 7/10 demonstration uses 7000000 and 10000000. `nonce` can be set for the new transaction. Amounts and keys must remain consistent with the saved recovery journal. This utility builds an initial pledge against a zero counter; it does not automatically add subsequent pledges.

The table describes the default 10/10 setup; optional amounts adjust the funding, shielding and recovery values as described below.

| Command | Output |
| --- | --- |
| `prepare` | Local keys, masks, nonces and immutable one-time payout/refund destinations. Verifies encryption/decryption for locally owned outputs. |
| `new-args` | Public native-CBOR constructor arguments. |
| `condition` | Official single-leaf spend-condition root for the verified authority badge. |
| `shield` | Public bootstrap instructions for 11 tTARI: 10 for funding and 1 for private fees. The public fee account is separate. |
| `fund` | Private funding proof and recovery journal plus unsigned transaction. Writes a 10 tTARI script-only pledge and 0.9 tTARI private fee change; the fee lane consumes 0.1 tTARI. |
| `dry-seal` / `seal` | Exact signed envelope and transaction ID. Uses only one-time source and fee signing keys. |
| `claim-args` | A private payout proof to the constructor's fixed one-time destination. The creator still must authorize execution after quorum and the required vote. |
| `refund-args` | A private refund proof for the single demonstration pledge to its fixed refund destination. The contract rejects it before the deadline or after payout. |

With partial funding, source/refund outputs use `funding_units`, the payout output uses `target_units`, shielding totals the source plus its separate private fee output, and the funding proof updates the counter by the actual contribution. `claim-args` refuses a partial single-pledge recovery: a completed multi-pledge campaign needs every pledge's private recovery and a combined payout proof. `refund-args` can recover the initial unpaid partial pledge after the deadline.

Before sealing, an external orchestrator must resolve inputs on `fund-unsigned.json` and save `fund-resolved.json`. The signer checks that only input declarations changed. Dry-run the exact transaction with the pinned Esmeralda indexer, journal the actual signed envelope before broadcast, then verify a committed receipt and the native output authority/counter. Reconcile an ambiguous response using the saved transaction ID; do not regenerate or re-fund. The CLI deliberately does not automate those consequential steps.

`claim-args` and `refund-args` only prepare arguments. Neither command checks live eligibility or sends a transaction. On-chain requirements remain authoritative. Use the private journals and their original configuration together for recovery. The actual demonstration's principal remains locked pending the required community vote; see [receipts and privacy limits](../../docs/private-escrow-testnet.md).
